3. P1 高优先级缺陷

P1-1 Web 产物按发布说明直接打开必然白屏，子路径部署同样失败

位置

vite.config.ts（缺少 base 配置） → web-demo-dist.zip/index.html

实测证据
<!-- web-demo-dist.zip 解压后的 index.html -->
<script type="module" crossorigin src="/assets/index-CCA33FBM.js"></script>
<link rel="stylesheet" crossorigin href="/assets/index-DHICUq_7.css">

用无头 Chromium 以 file:///tmp/filedemo/index.html 打开（--virtual-time-budget=4000 --dump-dom）：

root 片段: id="root"></div>      ← React 未挂载，容器为空
DOM 总长: 1120                      ← 仅为原始 HTML 骨架
根因与影响
  • Vite 默认 base: '/'，产出绝对路径资源引用。file:// 下 /assets/… 解析为文件系统根目录 file:///assets/…，必定 404。
  • Release 页面与发布说明明确写着「解压后任意静态服务器托管，或直接用浏览器打开 index.html」——按说明操作的 100% 用户遇到白屏。
  • 「任意静态服务器托管」也不成立：部署到子路径（如 https://example.com/battery/）时 /assets/ 指向域名根，同样 404。
  • CI 的「Verify Web Dist Output」只检查 index.html 非空与 assets/ 下文件数 ≥ 2，完全不校验资源路径可达性，因此该缺陷被门禁放行。
修复建议
// vite.config.ts
export default defineConfig(() => ({
  base: './',          // 关键：改为相对路径
  plugins: [react(), tailwindcss()],
  ...
}));

另外在 CI 增加一步真实加载校验（无头浏览器打开 file://dist/index.html 并断言 #root 有子节点 / 关键文案出现），重新构建并替换 Release 资产与 SHA256SUMS.txt。

P1-2 CI 回归门禁存在「假绿灯」：无法覆盖本次修复的缺陷类型

位置

.github/workflows/build-apk.yml:90-93

- name: Run Startup Crash Regression Tests (Robolectric)
  run: |
    cd android
    ./gradlew testDebugUnitTest --no-daemon --stacktrace || gradle testDebugUnitTest ...
根因与影响
  • v1.2.4 的启动崩溃根因是 release 变体启用 R8 全量混淆后，ViewModel 反射所需构造器被移除；而 testDebugUnitTest 跑的是 debug 变体，isMinifyEnabled=false，代码完全未混淆。
  • 因此 StartupCrashRegressionTest（及全部 11 个测试类、1,980 行测试）在结构上永远不可能复现该类缺陷，测试全绿与「release 包能否启动」无关。
  • 实证补强：对 12 个测试文件执行 grep -rniE 'minif|proguard|R8|release|mapping|obfuscat' 返回空；全仓共 79 个 @Test，无一涉及混淆、minify 或 release 变体。即测试套件在编写时就没有把「R8 之后能否启动」列为验证目标。本次本地实跑这 79 个用例 failures=0 / errors=0 全部通过——「测试全绿」与「release 包能否启动」无关这一点得到实证。
  • CI 后续虽然执行 assembleRelease，但只有 aapt2 badging（包名/版本/图标/标签）与 apksigner verify（签名完整性），没有任何针对 minified release 产物的启动/反射冒烟。
  • 后果：v1.2.5 的修复本次确实生效，但任何后续改动只要再次破坏 keep 规则、或引入新的反射依赖，CI 依旧全绿并照样发布崩溃包——导致 v1.2.4 事故可以原样重演。
修复建议
  • 在 assembleRelease 之后增加 release 产物静态冒烟：解析 release APK 的 dex，断言 ViewModel 子类存在 <init>(Landroid/app/Application;)V（本次审计已用 androguard 验证此法可行）。
  • 或增加 testReleaseUnitTest / minified 变体的单元测试；更彻底的是引入 instrumentation 或 adb shell am start 启动冒烟。
  • 把 R8 mapping.txt 上传为 CI artifact，便于事后追溯混淆结果。

P1-3 Web 与 Android 双端判定口径全面脱节（4 个子项）

Release 摘要与 README 多处宣称「与 Web 端对齐 / 口径一致 / 双通道语义零漂移」，但 Web 端仍停留在 v1.2.2 之前的旧实现，Android 端 v1.2.3~v1.2.4 的修复一项都未同步到 Web。

子项Android 端（已修复）Web 端（未同步）
① 充满判定 BatteryTelemetryParser.evaluateFullCharge：percentage==100 && isCharging && abs(I)≤25，三态（FULLY_CHARGED / NOT_YET / CURRENT_UNAVAILABLE）、符号无关、校验充电态 useBatteryMonitor.ts:96、App.tsx:229/460/466/470、FullChargeCalibrationCard.tsx:31：percentage===100 && current>=0 && current<=25。要求电流为正 → 充电上报负电流的高通/三星机型永远无法触发充满；无充电态校验 → 拔线后 100% 且电流恰在 0~25 即误判；无「电流不可读」三态
② 功率方向 v1.2.4 P2 已移除 abs()：powerWatts = V × I / 1e6，充电 +W / 放电 −W useBatteryMonitor.ts:207、App.tsx:259/444/537/540 全部 Math.abs(V*I)，充放电同显正功率，方向信息丢失
③ 温度阈值 v1.2.4 P2 统一单源：TEMP_WARM=38 / TEMP_OVERHEAT=45，温度卡与节流标签共用 Web 内部自相矛盾：useBatteryMonitor.ts:64 用 ≥44 / ≥38.5，App.tsx:100-101 用 >45 / ≥38。→ 44~45℃ 节流标签「重度节流」而温度卡「偏热预警」；38~38.5℃ 反之。正是 Android 端已修复的同屏矛盾 bug，在 Web 端完整复现
④ 容量区间 v1.2.3 扩为 500~25000 mAh（注释明确记载「移除 1000~15000 二次钳制，避免真实设备被静默改写」） useBatteryMonitor.ts:281、DevicePresetSelector.tsx:39/150-151、HardwareSimulationLab.tsx:324-325/338-340 仍是 1000~15000 mAh
影响

作为「同源双端」产品，用户在 Web 演示端看到的判定结果与 Android 真机不一致；发布说明「双端口径一致」的宣称失实。Web 演示本身是完整交付资产（web-demo-dist.zip），不是可忽略的内部工具。

修复建议

把判定谓词、阈值常量、容量区间抽成两端共享的规范（或至少在 Web 端建立 src/constants/telemetry.ts 与 Android BatteryTelemetryParser 常量表逐项对齐，并加一条双端口径一致性测试）。

4. P2 中优先级缺陷

P2-1 EXTRA_PLUGGED 默认值 -1 被当作「已充电」，引发符号翻转与双通道判定漂移

位置

android/app/src/main/java/com/battery/master/service/BatteryTelemetryParser.kt:261-263

val isCharging = status == BatteryStatus.CHARGING || status == BatteryStatus.FULL ||
    ((intent?.getIntExtra(BatteryManager.EXTRA_PLUGGED, -1) ?: -1) != 0)
val currentMa = BatterySysfs.normalizeCurrentToMilliAmps(rawCurrentProp, isCharging)
根因
  • 当 intent == null（registerReceiver(null, filter) 在异常 ROM 上失败）或该 extra 缺失时，getIntExtra 返回 -1，而 -1 != 0 为 true → 恒判「充电中」。
  • 后果一：normalizeCurrentToMilliAmps 依 isCharging 校准符号，放电负电流被翻转为正值，指标 11 方向显示错误。
  • 后果二（更关键）：evaluateFullCharge(percentage, currentMa, isCharging) 因 isCharging=true 可能在 100% 拔线放电时误判 FULLY_CHARGED —— 与 v1.2.3 P0 声称修复的「防拔线误判」直接冲突。
双通道漂移（结构性）

Parser 的 isCharging 含 EXTRA_PLUGGED 兜底，而 BatteryReceiver.kt:55-57 与 BatteryHardwareReader.kt:124 的 isCharging 只看 status==CHARGING||FULL。于是可能出现：Parser 算出 FULLY_CHARGED 并把 UI 状态强制为 FULL、显示「已达充满判定」，但 lockFullChargeIfCriteriaMet 因 isCharging=false 不写盘 → isFullChargeConditionMet=true 却 fullChargeSource=NONE、指标 12 无容量。README 第 60 行「双通道语义完全一致」的宣称在此被打破。

修复建议
val plugged = intent?.getIntExtra(BatteryManager.EXTRA_PLUGGED, 0) ?: 0
val isCharging = status == BatteryStatus.CHARGING || status == BatteryStatus.FULL || plugged > 0

并把该 isCharging 随 RawBatteryTelemetry 透传，让广播/轮询锁定逻辑消费同一判定，消除两套口径。

为何 79 个测试没发现它

CoreDefectAuditTest.kt:52 与 :102 构造 Intent 时都显式执行了 putExtra(EXTRA_PLUGGED, BATTERY_PLUGGED_AC)，恰好绕开「extra 缺失 → 默认值 -1」这条路径；:77 则直接调用 evaluateFullCharge(100, 16, isCharging = false)，绕过 Parser 内部计算 isCharging 的逻辑。缺陷因此被测试用例本身屏蔽。建议补一条「无 EXTRA_PLUGGED + DISCHARGING」的用例。

P2-2 发布说明「声明权限数：0」与最终 APK 不符

实测证据

源码 AndroidManifest.xml 确为 0 权限，但最终发布 APK 经 manifest merger 合并出：

<permission android:name="com.battery.master.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION"
            android:protectionLevel="0x00000002"/>   <!-- signature -->
<uses-permission android:name="com.battery.master.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION"/>

来源是 BatteryViewModel.kt:90-95 使用 ContextCompat.registerReceiver(..., RECEIVER_NOT_EXPORTED)，AndroidX Core 为兼容旧平台自动注入该签名级权限。

影响

该权限本身无害、非敏感、非运行时权限（protectionLevel=signature），不影响「零敏感权限」的产品定位；但 Release 页「声明权限数：0」与 README 第 75 行「Manifest 零权限声明」按字面与扫描结果不符，应用商店合规问卷 / 隐私清单按 0 填写会被自动化扫描打回。

修复建议

说明改为「0 个运行时/危险权限；1 个 AndroidX 自动注入的签名级内部权限（DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION）」；或评估在 Manifest 用 tools:node="remove" 移除并确认 API 33+ 行为不受影响。

P2-3 apksigner verify | head -n 10 使签名校验退出码语义不可靠

位置

.github/workflows/build-apk.yml:166

"$APKSIGNER" verify --verbose "$APK_PATH" | head -n 10 || { echo "::error::APK signature verification failed"; exit 1; }
根因

管道 + head 会提前截断 stdout。若未启用 pipefail，apksigner 校验失败（退出非 0）但 head 成功返回 0，|| 分支不会触发——无效签名可被发布；若启用 pipefail，--verbose 输出超 10 行时 apksigner 收到 SIGPIPE 非 0，反而误报失败。两种情形都不可靠。发布说明把「无条件 apksigner verify」列为 v1.2.4 的门禁修复，实际校验强度不足。

修复建议
"$APKSIGNER" verify --verbose "$APK_PATH" > verify.txt 2>&1 || { cat verify.txt; exit 1; }
head -n 10 verify.txt

P2-4 CI 注入的 KEY_ALIAS Secret 从未被 Gradle 读取，keyAlias 硬编码

位置

build.gradle.kts:29-37 与 build-apk.yml:63-80

// build.gradle.kts

    releaseKeystorePass != null && releaseKeyPass != null   // 不校验 alias

影响
  • triggerFullChargeSimulation() 立即写入 simulationHoldUntilMs，但 _simulationRemainingSec 最多 500ms 后才变为 >0。而 FullChargeConditionCard 的按钮 enabled = !isSimulating（simulationRemainingSec > 0）——这 500ms 内按钮仍可重复点击，导致反复写 SharedPreferences、反复重置 15 秒保持期。
  • catch (e: Throwable) 覆盖 delay(500)，会吞掉协程的 CancellationException。虽因随后的 delay(250) 在 try 外仍会完成取消，但属于典型的协程反模式，在后续重构中极易演变成无法取消的僵尸协程。
  • 方法注释仍写「每 250ms 刷新剩余秒数」，与新的 500ms 低频逻辑不符。
修复建议

在 triggerFullChargeSimulation() 中同步 _simulationRemainingSec.value = SIMULATION_HOLD_MS / 1000；catch 改为 catch (e: Exception) 并显式 if (e is CancellationException) throw e（或改用 ensureActive()）；同步更新注释。

P2-6 清除充满记录后，采集异常降级会让已删除的锁定值「复活」

位置

BatteryHardwareReader.kt:93, 98-104 与 BatteryViewModel.kt:375-386

fun readBatteryTelemetry(): BatteryState = try {
    readBatteryTelemetryInternal().also { lastKnownState = it }
} catch (e: Throwable) {
    lastKnownState ?: buildSafeDefaultState()   // 返回旧快照
}

clearFullChargeRecords() 清除了内存字段与 SharedPreferences，并通过 VM 更新了 _batteryState，但未清除 reader.lastKnownState 快照。若此后某一拍 readBatteryTelemetryInternal() 抛异常（ROM 服务异常、sysfs 拒绝等，代码本身已为此设计了兜底），将返回清除前的旧快照，指标 12 的「已清除」锁定容量重新出现。

修复建议

clearFullChargeRecords() 中同步 lastKnownState = null，或把快照的 fullCharge 字段一并清空。

P3-6 APK 仅 v2 签名，缺少 v3 / v3.1

实测 is_signed_v1=false, v2=true, v3=false, v3.1=false；jarsigner 显示「jar is unsigned」（无 v1 JAR 签名）。minSdk 26 下 v2（API 24+）完全够用、可正常安装，不是安装缺陷；但缺少 APK 密钥轮换能力（Android 13+ 的 v3.1），未来更换签名证书需用户卸载重装。

P3-7 发布产物缺 VCS 溯源信息

APK 内 META-INF/version-control-info.textproto 内容为 generate_error_reason: NO_SUPPORTED_VCS_FOUND，说明 CI checkout 未携带 git 历史，产物无法反查构建 commit。建议 actions/checkout@v4 设置 fetch-depth: 0。
