# BatteryData v1.5 功能提升改善 — 详细技术规划方案

> 基线:Release v1.0.13(versionCode 113)| 撰写视角:产品经理 × 技术规划
> 定位:从「电池数据展示工具」升级为「电池管理平台」

---

## 一、版本定位与产品目标

v1.0.x 系列已经完成了"看得见"的目标:电量、电压电流功率、健康度、充电记录、灵动岛、更新链全部跑通并在真机闭环。v1.5 要解决的核心问题是**"看得懂、管得住、留得住"**:

| 产品目标 | 含义 | 衡量指标 |
|---|---|---|
| 看得懂 | 数据 → 结论(健康趋势、充电习惯、损耗预测) | 健康趋势页人均访问 ≥ 2 次/周 |
| 管得住 | 数据 → 行动(充电提醒、快充识别、护充建议) | 自动充电记录开启率 ≥ 40% |
| 留得住 | 长期数据资产(历史曲线、报告导出) | 7 日留存 ≥ 25% |

---

## 二、v1.0.13 现状盘点与痛点(基于真实审计结论)

### 已有模块(48 个源文件)

| 模块 | 文件 | 现状 |
|---|---|---|
| 数据采集 | BatteryRepository / SysfsBatteryReader / BatterySample | 1 秒流、四级兜底(系统层→sysfs→库仑计差分→典型值)、电池目录缓存 |
| 实时数据 | RealtimeStatsCard / LiveChartCard | 电压/电流/功率 3 位小数、每秒刷新、温度 |
| 健康度 | BatteryHealthCard / DesignCapacityResolver | 满电/设计容量、机型库 135 条(小米/OPPO/vivo/一加)、系统健康状态文字版 |
| 充电记录 | ChargeRecorder / ChargeRecordService / ChargeRecordStore / RecordsScreen / ChargeDetailScreen | 状态机(去重/carryOver/重启检测)、前台服务自动记录、JSON 存储、详情页图表 |
| 超级岛 | BatteryIslandHelper / FluidCloudHelper | 小米灵动岛 + OPPO 流体云 + 谷歌兜底通知,调度链 |
| Shizuku | ShizukuManager / PrivilegedServiceImpl | 特权读节点/防火墙放行 |
| 小部件 | BatteryWidgetProvider | 基础电量小部件 |
| 更新 | UpdateChecker / ApkUpdater | 6 源清单+多源下载、ZIP 完整性校验、固定签名 |
| 诊断 | LogFileStore / UiDiagnostics / LogDiagnosticScreen | 日志导出、UI 埋点 |

### 六大痛点(1.5 的立项依据)

1. **数据不留痕**:实时数据每秒采集但秒后即弃,没有历史;健康度只有"当下值",看不到"变化趋势"。
2. **充电记录依赖前台服务**:服务被 ROM 杀掉就漏记;没有充电习惯分析(时段/频率/快慢)。
3. **快充是黑盒**:用户最关心的"我到底跑的什么快充"(PD/QC/VOOC/SCP)完全没有展示。
4. **灵动岛 ROM 覆盖窄**:只适配小米/OPPO,vivo(OriginOS 灵动窗口)与鸿蒙(实况窗)用户无法享受。
5. **小部件太基础**:只有电量,没有健康度/预估时间/充电状态,无实时性保障。
6. **无统一设置页**:开关散落在首页菜单与关于页,能力多了以后不可维护。

## 三、v1.5 功能提升方案(六大方向)

### 方向 1:电池历史与趋势(核心,P0)

**用户价值**:把"今天 92%"变成"三个月从 98% 掉到 92%,老化速度偏快"。

| 特性 | 技术方案 |
|---|---|
| 健康度历史追踪 | `HealthSnapshotStore`(JSON→Room 迁移的一部分):每天 1 条快照(fullChargeMah/design/healthPercent/cycleCount),采集时机=应用前台首次采样;存储 Room `health_snapshot` 表 |
| 趋势曲线页 | 新 `HealthTrendScreen`:30/90 天折线(Canvas 自绘,复用 LiveChartCard 的绘制骨架);显示"月损耗率"(%/月),与同机型库基准对比 |
| 老化预测 | 线性回归(≥14 个快照才启用):`预计健康度 80% 剩余天数 = (当前-80)/月损耗率`;不足 14 天显示"积累数据中" |
| 报告导出 | `HealthReportExporter`:生成 PNG 分享卡(趋势+关键指标)与 CSV 原始数据,走系统分享 |
| 实时功耗历史 | Repository 内存环形缓冲(最近 10 分钟,1Hz)→ RealtimeStatsCard 顶部迷你功耗曲线,进程内零成本 |

**依赖**:Room 引入(替代 ChargeRecordStore JSON);WorkManager 不需要(前台采样即可)。

### 方向 2:快充协议识别与充电体验(P0)

**用户价值**:回答"插上充电器,我到底在用什么协议、多久充满"。

| 特性 | 技术方案 |
|---|---|
| 充电类型识别 | sysfs `charge_type` 节点(Standard/Delivery/Proprietary)+ `constant_voltage`/`input_current_limit`;无 Shizuku 时降级用功率档位推断(≥50W 逻辑=电流×电压) |
| 协议标签 UI | BatteryHeroCard 充电状态区显示协议徽标(PD / QC / 私有快充 / 慢充),估算档位标注 |
| 0→80% 耗时统计 | 充电记录新增分段计时(基于每秒采样的 level 序列):0-80 快充段 / 80-100 涓流段耗时,详情页展示 |
| 充满提醒 | ChargeRecordService 内加通知:达到用户设定阈值(默认 90%)单次提醒;借用现有通知去重通道 |
| 充电习惯分析 | RecordsScreen 统计区:周充电次数/平均时长/快充占比/夜间充电占比(时段直方图) |

**依赖**:charge_type 节点在部分机型需 Shizuku → 与方向 5 联动("无 Shizuku 也能看功率推断")。

### 方向 3:灵动岛 ROM 扩展(P1)

**用户价值**:vivo/华为用户也能用岛。

| 特性 | 技术方案 |
|---|---|
| vivo OriginOS 灵动窗口 | 调研 OriginOS `VivoCustomDialog`/胶囊 API;不可行则降级为悬浮窗方案(系统 alert window,复用现有 FluidCloudHelper 的内容渲染) |
| 鸿蒙实况窗 | API 无法从三方直接调 → 降级为前台通知 + `LiveUpdate`(待开源资料);鸿蒙识别 via `ro.build.display.id` |
| 调度链扩展 | 现有 小米→OPPO→谷歌兜底 扩为 小米→OPPO→vivo→鸿蒙→谷歌;`IslandProvider` 接口抽象(每家一个 Helper 实现选择器) |
| 岛内容丰富化 | 充电功率实时显示(已在岛上的电量旁加 W 数);健康预警透传(系统健康异常红标) |

**依赖**:vivo/华为 API 可达性有不确定性 → 先出**悬浮窗降级方案**,保证功能可用性。

### 方向 4:小部件升级(P1)

| 特性 | 技术方案 |
|---|---|
| 三种尺寸 | 小(电量环)/ 中(电量+预估可用时间+充电状态)/ 大(加健康度+循环);Glance 或继续 RemoteViews(现有 BatteryWidgetProvider 扩展,不加依赖) |
| 实时性 | 现有 updatePeriodMs 系统最低 30 分钟 → 增加充电中每 1 分钟主动更新(由 ChargeRecordService 驱动 `AppWidgetManager.update`),非充电靠系统周期 |
| 点击直达 | 点击跳对应页(主界面/记录页),`PendingIntent` 固定 route |

### 方向 5:统一设置页(P1)

| 特性 | 技术方案 |
|---|---|
| SettingsScreen | 新页面聚合:岛开关/流体云开关、充满提醒阈值、刷新率(1s/2s/省电 5s)、数据导出入口、Shizuku 状态、关于 |
| 设置存储迁移 | BatterySettings SharedPreferences → DataStore(类型安全+Flow 响应式);存量 key 迁移逻辑 |
| 免打扰 | 充电记录服务通知可降级为静默(low importance),默认保持 |

### 方向 6:更新与分发加固(P2)

| 特性 | 技术方案 |
|---|---|
| Gitee 镜像源 | 仓库镜像 + `update/latest.json` 同步,UpdateChecker 源列表加 Gitee raw(国内稳定性再抬一档) |
| 更新日志页 | 检查更新弹窗内嵌 markdown 渲染 notes,替代纯文本 |
| 灰度验证 | release.yml 产物验证步骤加 zipalign 检查与最低 size 阈值,坏包在 CI 阶段拦截 |

## 五、技术架构演进

1. **存储层**:引入 Room(充电记录表 + 健康快照表 + 充电事件分段表);ChargeRecordStore 改为 Room DAO,一次性迁移存量 JSON(版本号字段守护,失败回退读旧文件)。
2. **设置层**:SharedPreferences → DataStore,`BatterySettings` 改造为 `Flow<T>` 响应式读取,UI 层 collectAsState。
3. **岛抽象**:`IslandProvider` 接口(support()/show()/hide()),四家 Helper 注册进选择器,调度链由硬编码顺序改为优先级列表。
4. **图表**:LiveChartCard 的 Canvas 绘制骨架抽公共 `LineChart` 组件,健康趋势/功耗曲线/充电分段曲线三处复用。
5. **测试**:Repository/Recorder 状态机补 JVM 单测(不依赖 Android SDK,本地可跑);CI 加 `testDebugUnitTest` 步骤。

## 六、风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| vivo/鸿蒙岛 API 不可达 | 方向 3 核心特性跳票 | 先做悬浮窗降级(技术确定性 100%),原生 API 作为增强 |
| charge_type 节点 SELinux 锁死 | 快充识别降级 | 功率档位推断兜底(≥50W/≥25W 分档),与实时数据四级兜底同思路 |
| Room 迁移丢数据 | 用户充电记录丢失 | 迁移前备份旧 JSON;失败自动回退旧读路径 |
| 每秒流+Room 写入功耗 | 电量消耗上升 | 健康快照每天 1 条(非每秒);实时数据仍走内存环形缓冲 |
| CI 无 Android SDK 级单测环境 | testDebugUnitTest 失败 | 单测限定 JVM 模块(纯 Kotlin 状态机/公式),Robolectric 缓引 |

## 七、数据指标(上线后验证)

- 自动充电记录开启率(目标 ≥40%)
- 健康趋势页人均访问 ≥2 次/周
- 小部件添加率 ≥15%
- 更新成功率(v1.5 版本 7 日内升级占比 ≥60%,验证更新链加固效果)
- 崩溃率 <0.1%(UiDiagnostics 埋点统计)
